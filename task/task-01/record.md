# LLM Agent 设计模式演进路线

## 一、为什么提出这种渐进式模式？

大语言模型（LLM）本身只是一个"文本接龙"引擎——给它输入，它输出下一个 token。但当我们希望 LLM 像真正的**智能体（Agent）**一样自主地解决问题时，仅仅一次"输入→输出"远远不够。

本书（《Hello Agents》）在 `task-01` 中采用了一种**渐进式构建**的教学路线，从最基础的 LLM 调用开始，逐步叠加"规划"、"行动"、"反思"三大核心能力，最终形成一个完整的 Agent 架构。这种设计的根本原因在于：

1. **认知递进**：学习者需要从零开始，先理解 LLM 本身的能力边界，再逐步引入外部机制来弥补这些边界。
2. **能力解耦**：每种模式聚焦解决一类特定问题（推理、规划、交互、自我改进），避免一次性引入过多概念。
3. **工程实践**：在真实工程中，不同复杂度的任务需要不同复杂度的模式，渐进式路线帮助开发者建立"按需选型"的判断力。

---

## 二、四种模式概览与优劣势分析

### 2.1 LLM Client（基础调用模式）

> 对应文件：`llm_client.py`

**核心思想**：将 LLM 封装为一个可调用的客户端，通过 `messages` 列表进行单轮或多轮对话，直接获取模型的文本输出。

**架构**：
```
用户 → [Messages] → LLM → 文本响应
```

**优势**：
- ✅ **极简**：代码量最少，概念最清晰，是理解一切 Agent 模式的基石
- ✅ **通用**：适用于任何需要 LLM 生成文本的场景
- ✅ **可控**：开发者完全掌控输入输出的格式和流程
- ✅ **低延迟**：单次调用，无额外循环开销

**劣势**：
- ❌ **无状态**：每次调用独立，不具备记忆和上下文积累能力
- ❌ **无工具**：无法与外部世界交互，只能依赖模型内部知识
- ❌ **无规划**：面对复杂问题时，一次性生成的质量不稳定
- ❌ **无反馈**：不能自我检查或纠正错误

---

### 2.2 Plan-and-Solve（规划-执行模式）

> 对应文件：`Plan_and_solve.py`

**核心思想**：在 LLM Client 的基础上引入**规划器（Planner）**和**执行器（Executor）**两个角色。Planner 将复杂问题分解为有序的子步骤列表，Executor 按顺序逐步执行每个子任务，并将历史结果传递给后续步骤。

**架构**：
```
用户问题
   ↓
[Planner] → 生成步骤列表 ["步骤1", "步骤2", ...]
   ↓
[Executor] → 逐步执行，累积历史 → 最终答案
```

**优势**：
- ✅ **结构化推理**：将复杂问题分解为简单子任务，降低单步推理难度
- ✅ **可追溯**：每一步都有明确的输入和输出，便于调试和理解
- ✅ **上下文传递**：历史步骤的结果被显式传递给后续步骤，避免信息丢失
- ✅ **适合多步计算**：对数学应用题、逻辑推理等有显著效果提升

**劣势**：
- ❌ **计划僵化**：一旦生成计划，执行过程不会动态调整，无法根据中间结果修正方向
- ❌ **无外部交互**：所有步骤仍然只依赖 LLM 内部知识，不能搜索或调用工具
- ❌ **计划质量依赖模型能力**：如果 Planner 生成了错误的分解，后续执行全部偏离
- ❌ **无自我反思**：执行完成后不会回头检查整体结果的正确性

---

### 2.3 ReAct（推理-行动模式）

> 对应文件：`ReAct.py` + `tools.py`

**核心思想**：在 Plan-and-Solve 的基础上引入**外部工具调用**能力。模型在每一步先进行**思考（Thought）**，然后决定采取一个**行动（Action）**——调用某个工具或给出最终答案，接着获取工具的**观察结果（Observation）**，再基于观察继续思考，形成 `Thought → Action → Observation` 的循环。

**架构**：
```
用户问题
   ↓
┌→ Thought: 分析当前情况，决定下一步
│   ↓
│  Action: 调用工具 tool_name[input] 或 Finish[答案]
│   ↓
│  Observation: 工具返回的结果
│   ↓
└── 循环，直到 Action = Finish
```

**优势**：
- ✅ **动态决策**：每一步都根据最新的观察结果重新决策，而非僵化执行预设计划
- ✅ **工具扩展**：通过 `ToolExecutor` 注册任意工具（搜索、计算、API 调用等），极大扩展了 Agent 的能力边界
- ✅ **实时信息**：可以调用搜索引擎获取最新数据，突破 LLM 知识截止日期的限制
- ✅ **自适应终止**：模型自主判断何时已收集足够信息，输出最终答案

**劣势**：
- ❌ **缺乏全局规划**：每一步都是局部决策，可能在复杂任务中"走一步看一步"，效率较低
- ❌ **容易陷入循环**：如果工具返回的信息不充分，模型可能反复调用同一工具
- ❌ **Token 消耗高**：每一轮循环都需要将完整历史重新发送给 LLM
- ❌ **无自我改进**：完成任务后不会反思过程，无法从经验中学习

---

### 2.4 Reflection（反思-迭代模式）

> 对应文件：`Reflection.py`

**核心思想**：在基础执行之上引入**反思（Reflection）**机制。Agent 先执行任务生成初始输出，然后由一个"评审员"角色对输出进行严格审查并提出改进建议，最后根据反馈优化输出。这个"执行→反思→优化"的循环会迭代多轮，直到评审员认为输出已无需改进。同时引入**记忆模块（Memory）**来存储完整的执行与反思轨迹。

**架构**：
```
用户任务
   ↓
[初始执行] → 生成初始输出（代码）
   ↓
┌→ [反思/评审] → 分析不足，提出改进建议
│   ↓
│  检查：是否"无需改进"？ → 是 → 结束
│   ↓ 否
│  [优化执行] → 根据反馈生成改进版本
│   ↓
└── 循环，直到满意或达到最大迭代次数
   ↓
最终输出
```

**优势**：
- ✅ **自我改进**：通过多轮迭代不断优化输出质量，显著提升代码、文章等生成物的水准
- ✅ **角色分离**：执行者和评审者使用不同的 Prompt，各司其职，评审者专注于找问题
- ✅ **记忆轨迹**：Memory 模块记录了完整的执行-反思历史，便于追溯和调试
- ✅ **质量可控**：通过 `max_iterations` 控制迭代次数，平衡质量与成本

**劣势**：
- ❌ **Token 消耗最高**：每轮迭代至少需要 2 次 LLM 调用（反思 + 优化），成本是其他模式的数倍
- ❌ **收敛不确定**：模型可能无法真正收敛，迭代多轮后仍有改进空间
- ❌ **局限于生成任务**：主要适用于代码生成、文本润色等可迭代的创作型任务
- ❌ **无外部工具**：当前实现中没有引入工具调用能力，无法获取外部信息

## 三、渐进式演进路线

下面这张图展示了四种模式之间的演进关系，每一层都在前一层的基础上增加了一项关键能力：

```
┌─────────────────────────────────────────────────────────┐
│                    Reflection 反思模式                    │
│  + 自我反思与迭代优化能力                                  │
│  + Memory 记忆模块                                       │
│  核心循环: 执行 → 反思 → 优化                              │
├─────────────────────────────────────────────────────────┤
│                     ReAct 推理-行动模式                    │
│  + 外部工具调用能力                                       │
│  + Thought-Action-Observation 循环                       │
│  核心循环: 思考 → 行动 → 观察                              │
├─────────────────────────────────────────────────────────┤
│                  Plan-and-Solve 规划-执行模式               │
│  + 任务分解与规划能力                                      │
│  + Planner / Executor 角色分离                            │
│  核心流程: 规划 → 逐步执行                                 │
├─────────────────────────────────────────────────────────┤
│                   LLM Client 基础调用模式                  │
│  = 单次 LLM 调用                                         │
│  = 输入 Messages → 输出文本                                │
│  一切 Agent 模式的基石                                     │
└─────────────────────────────────────────────────────────┘
```

### 演进逻辑详解

| 演进阶段 | 新增能力 | 解决的问题 | 关键代码组件 |
|---------|---------|-----------|-------------|
| **LLM Client** | 基础对话 | 让 LLM 能"说话" | `HelloAgentsLLM.think()` |
| **+ Plan-and-Solve** | 任务规划 | 让 LLM 能"想清楚再做" | `Planner` + `Executor` |
| **+ ReAct** | 工具交互 | 让 LLM 能"动手查资料" | `ToolExecutor` + `Thought/Action/Observation` 循环 |
| **+ Reflection** | 自我反思 | 让 LLM 能"做完之后检查和改进" | `Memory` + 反思-优化迭代循环 |

**核心洞察**：这四种模式并非互相替代的关系，而是**能力叠加**的关系。一个完整的、生产级的 Agent 系统往往同时具备规划、工具调用和自我反思三种能力。本书将它们拆分为四个独立模式，是为了让学习者逐步理解每个能力的价值和实现方式。

## 四、应用场景与模式选型

### 4.1 LLM Client — 简单对话与文本生成

**适用场景**：
- 聊天机器人、客服问答
- 文本翻译、摘要、改写
- 代码补全、简单代码生成
- 任何**单轮即可完成**的文本生成任务

**示例**：
> "帮我把这段英文翻译成中文"
> "写一个快速排序算法"

**选型理由**：任务简单明确，一次调用即可得到满意结果，无需引入额外的复杂性。

---

### 4.2 Plan-and-Solve — 多步推理与复杂计算

**适用场景**：
- 数学应用题求解
- 多步骤逻辑推理
- 项目计划制定
- 数据分析报告生成（先分析各维度，再汇总）
- 任何需要**分步骤、有条理地解决**的问题

**示例**：
> "一个水果店周一卖出15个苹果，周二是周一的两倍，周三比周二少5个，三天总共卖出多少？"

**选型理由**：问题可以预先分解为明确的子步骤，且每个子步骤之间具有线性依赖关系，适合"先规划、后执行"的策略。

---

### 4.3 ReAct — 信息检索与动态决策

**适用场景**：
- 实时信息查询（新闻、天气、股票等）
- 多源信息整合
- 需要调用外部 API 或数据库的任务
- 研究型任务（需要搜索、对比、综合多个来源）
- 任何**答案不在模型知识中**、需要**动态获取外部信息**的场景

**示例**：
> "2026华为最新的手机是哪一款？它的主要卖点是什么？"

**选型理由**：答案需要实时搜索获取，且可能需要多轮搜索（先搜手机型号，再搜具体参数），适合"边想边做、动态调整"的策略。

---

### 4.4 Reflection — 代码优化与质量提升

**适用场景**：
- 代码生成与优化（从暴力解法优化到最优算法）
- 文章润色与改写
- 方案设计（先出初稿，再根据反馈迭代）
- 测试用例生成与补充
- 任何**输出质量可以通过迭代显著提升**的创作型任务

**示例**：
> "编写一个Python函数，找出1到n之间所有的素数"（初始可能用试除法，反思后优化为埃拉托斯特尼筛法）

**选型理由**：任务的输出有明显的"好坏"之分，通过引入"评审者"角色的反馈，可以系统性地提升输出质量。

---

### 4.5 模式组合 — 生产级 Agent

在真实的工程实践中，上述模式往往**组合使用**：

| 组合方式 | 描述 | 典型场景 |
|---------|------|---------|
| Plan-and-Solve + ReAct | 先规划步骤，每步执行时可调用工具 | 复杂研究报告（先列大纲，每节搜索素材） |
| ReAct + Reflection | 执行后反思结果质量，不满意则重新搜索 | 高精度信息核实 |
| Plan-and-Solve + Reflection | 规划执行后反思整体方案，优化下一轮计划 |  iterative 软件开发 |
| 全部组合 | 规划 → 工具执行 → 反思 → 再规划 | 自主编程 Agent（如 Devin、Cursor Agent） |

---

## 五、总结

本书 `task-01` 的四种模式构成了一条清晰的**能力进化链**：

```
能说话 → 能规划 → 能行动 → 能反思
```

每一种模式都是对前一种的**增强和补充**，而非替代。理解每种模式的核心思想、优劣势和适用场景，是构建更复杂 Agent 系统的基础。在实际应用中，应根据任务的复杂度、实时性要求和质量需求，灵活选择和组合这些模式。
